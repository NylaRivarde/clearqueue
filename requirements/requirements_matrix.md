# Requirements Matrix — ClearQueue

This matrix translates the business problem (fragmented visibility into outstanding policy work) into structured requirements, scoped to a **Commercial Property underwriter's** book of business. Priority uses **MoSCoW** (Must / Should / Could / Won't-for-now); rationale ties each requirement back to an observed pain point. This is a proposed requirements set for a portfolio concept — it has not been through formal stakeholder sign-off.

**Version note:** This matrix has been revised twice after review. The first revision sharpened the product beyond "consolidate data onto one dashboard" by adding an explainable prioritization mechanism (Attention Score — UR-06/FR-08) and an account-level drill-down concept (Account 360 — UR-07/FR-09), and narrowed scope to Commercial Property so requirements reference real underwriting workflow (COPE, four-point inspections, elevation certificates) instead of generic policy status. The second revision (FR-10) removed account size from the Attention Score formula and required it be shown as a separate signal instead — see [Attention Score Model](../analysis/attention_score_model.md) for the full reasoning.

Legend: **BR** = Business Requirement · **UR** = User Requirement · **FR** = Functional Requirement · **NFR** = Non-Functional Requirement · **DR** = Data/Reporting Requirement

| ID | Type | User/Business Need | Requirement | Priority | Rationale | Related Feature |
|---|---|---|---|---|---|---|
| BR-01 | BR | Leadership needs to reduce time spent manually assembling status reports | The product must provide a shared, always-current view of outstanding policy work without requiring manual data extraction | Must | Managers currently rebuild Excel summaries by hand for regional distribution; this is the core problem statement | Team View, Regional Roll-Up |
| BR-02 | BR | Underwriters need to be accountable for their book without chasing status from multiple people/systems | The product must let an underwriter see the full status of their own book of business in one place | Must | Underwriters are accountable for outstanding items even though issuance execution sits with UAs | My Attention Queue |
| UR-01 | UR | Underwriter: "What needs my attention today?" | As an underwriter, I need a prioritized list of open items on my book, ranked by aging and urgency | Must | Directly answers the central product question | My Attention Queue |
| UR-02 | UR | Underwriting Assistant: manage a personal workload consistently | As a UA, I need to see and update the outstanding items I own without re-entering the same info in multiple trackers | Must | UAs currently maintain ad hoc personal tracking methods | Outstanding Item Log |
| UR-03 | UR | Manager: understand team-wide bottlenecks | As a manager, I need to see outstanding volume and aging broken out by underwriter/UA so I can rebalance work or intervene | Must | Managers currently only get this via manual Excel pulls | Team View |
| UR-04 | UR | Regional leader: portfolio-level visibility without waiting for an email | As a regional leader, I need a live roll-up of outstanding work across teams instead of a periodic emailed spreadsheet | Should | Named directly in the observed workflow problem | Regional Roll-Up |
| UR-05 | UR | Underwriter: avoid renewal surprises | As an underwriter, I need visibility into upcoming renewals so I can act before they become urgent | Should | Renewal follow-up currently depends on memory/manual checking | Renewal Radar |
| UR-06 | UR | Underwriter: trust *why* something is ranked urgent | As an underwriter, I need to see the specific reason an item is flagged urgent — not just a color — so I can decide how to act (chase a broker vs. do the work myself) | Must | A flat priority label doesn't tell you what to do next; added after review to make the product about decisions, not just visibility | Attention Score |
| UR-07 | UR | Underwriter: get the full picture on one account without hunting across systems | As an underwriter, I need a single consolidated view of everything relevant to one account when I need to act on it | Should | This is the account-level "360" view — a queue tells you *what*, an account view tells you *everything you need to act* | Account 360 |
| FR-01 | FR | Support UR-01 | System shall display each open policy transaction with Attention Score, status, days outstanding, the specific reason it needs attention, and next-action owner | Must | Core data needed to answer "what needs attention, and why" | My Attention Queue |
| FR-02 | FR | Support UR-02 | System shall allow the responsible party to record/update an outstanding item and its owner for any open transaction | Must | Replaces personal, inconsistent tracking with one shared field set | Outstanding Item Log |
| FR-03 | FR | Support UR-01, BR-02 | System shall allow filtering/sorting by underwriter, UA, region, occupancy type, status, Attention Score/priority, and aging | Must | Different roles need different slices of the same underlying data | My Attention Queue, Team View |
| FR-04 | FR | Support UR-03, BR-01 | System shall provide a team-level summary view (counts by status/aging/priority, grouped by underwriter or UA) | Must | This is the exact view a manager currently rebuilds manually | Team View |
| FR-05 | FR | Support UR-04 | System shall provide a region-level roll-up view aggregating multiple teams | Should | Extends the team view up one level for regional leaders | Regional Roll-Up |
| FR-06 | FR | Support UR-05 | System shall surface transactions with a renewal date within a configurable look-ahead window (e.g., 30/60 days), and flag when a renewal also has an open outstanding item | Should | Enables proactive renewal handling instead of reactive; the overlap case (renewal + open blocker) is the highest-risk combination | Renewal Radar |
| FR-07 | FR | Reduce manual reporting effort | System shall support exporting any filtered view to a standard format (e.g., CSV/PDF) for distribution outside the tool | Could | Some stakeholders may still need to forward a snapshot even after a shared view exists; avoids forcing 100% tool adoption on day one | Export |
| FR-08 | FR | Support UR-06 | System shall calculate an Attention Score for every open item from a documented, transparent rule set (aging, deadline pressure, blocking severity, next-action ownership) and display the top reason behind each score | Must | Inconsistent informal prioritization was a named pain point; a black-box score would trade one trust problem for another. **Revised after review:** account size (TIV) was removed as a score input — see FR-10 and [Attention Score Model](../analysis/attention_score_model.md#account-significance-is-deliberately-excluded-from-the-score) | My Attention Queue, [Attention Score Model](../analysis/attention_score_model.md) |
| FR-09 | FR | Support UR-07 | System shall provide an account-level detail view consolidating risk characteristics (COPE), current workflow status, next action/owner, and renewal timing for a single selected account | Should | Named "Account 360" — the consolidated single-account view that gives the product its name; see [Account 360 IA](../prototype/account_360_ia.md) | Account 360 |
| FR-10 | FR | Prevent account size from distorting workflow urgency | System shall display account significance (TIV band) as a separate, clearly labeled signal (e.g., a badge) in the queue and in Account 360, and shall never combine it into the Attention Score or use it to affect sort order | Must | A large account with an easy outstanding item should not outrank a small account that is genuinely overdue and blocked; conflating "important" with "urgent" would undermine the score's explainability | My Attention Queue, Account 360, [Attention Score Model](../analysis/attention_score_model.md#account-significance-is-deliberately-excluded-from-the-score) |
| NFR-01 | NFR | Trust in the data | Data shown must be refreshed on a predictable, clearly displayed cadence (e.g., "last updated X minutes/hours ago") | Must | A dashboard perceived as stale will be abandoned in favor of asking a person directly | All views |
| NFR-02 | NFR | Appropriate access control | Users shall only see data appropriate to their role (own book, own team, or own region) unless granted broader access | Must | Underwriting data (accounts, premium) is sensitive; role-based visibility mirrors existing access boundaries | All views |
| NFR-03 | NFR | Usability under time pressure | Core "what needs attention" view must be understandable within seconds, without training | Should | Underwriters and UAs will check this frequently during a busy day; it must not require a manual | My Attention Queue |
| NFR-04 | NFR | Auditability | Changes to outstanding-item status should be timestamped and attributable to a user | Could | Supports trust in the data and future process analysis | Outstanding Item Log |
| DR-01 | DR | Reporting consistency | Underlying data model must define Days_Outstanding and Aging_Bucket identically across all views | Must | Prevents the exact fragmentation problem (different people calculating "outstanding" differently) this product is meant to solve | Data Model |
| DR-02 | DR | KPI reporting | System shall support the KPI definitions in the [KPI Framework](../analysis/kpi_framework.md) as native, calculated fields rather than manual formulas | Should | Manual KPI calculation in Excel is part of the current-state problem | KPI Framework |
| DR-03 | DR | Historical trending | System shall retain enough history to show whether outstanding volume/aging is trending up or down over time | Won't (MVP) | Valuable but requires a data retention/history strategy beyond a point-in-time view; deferred to Phase 2 | Roadmap Phase 2 |

## Notes on Scope Decisions

- Items marked **Won't (MVP)** are not rejected — they are explicitly deferred. See [MVP Prioritization](../analysis/mvp_prioritization.md) for the full reasoning.
- This matrix assumes underlying source data (policy status, dates, ownership) already exists somewhere in current systems, since the business problem is visibility and consolidation — not the absence of underlying data. Where that assumption doesn't hold, DR-01/DR-02 would need re-scoping after a real data-source assessment (see [Risks & Constraints](../README.md#risks--constraints)).
